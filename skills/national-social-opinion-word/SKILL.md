# 全国社情民意、提案与咨政报告 Word 写作与交付

新写或实质改稿执行“概念清楚、问题分析深入、案例熟悉易懂、数据及时、三条对策”的要求，署名与版式沿用2026年9月指定样稿，先读 [个人样稿与深度标准](references/personal-model-profile.md)。当次要求、新样稿优先；只审稿、纯排版或拆分不强制重写正文。

## 任务承接

- 从当前请求、已确认稿件及上下文恢复主题、篇次、受众、层级、篇幅、署名、样稿和交付形式。“以上六篇”“拆成单篇”先定位对应稿件，不重新索要已有材料或另选题。
- 一个文稿聚焦一个政策对象、核心问题和主要制度工具。批量稿逐篇独立，建议说明主责机关、执行程序及可观察结果，核对中央与地方权限。
- 仅排版或拆分时以确认正文为内容权威，保留文字和有意版式。原件另存保留，除非用户明确要求原位修改。只审稿或讨论不强制生成 Word。
- 需求明确直接推进。只有主题、报送层级或核心事实缺口会改变结果时才询问，同时推进不依赖答案的工作。为本用户新写或按个人样稿实质改稿，采用个人规范中已授权的署名，不重复询问；给他人改稿不自动替换作者。其他必要身份缺失时在交付说明列出，不编造或留下正文占位符。
- 用户要求“生成前确认”时，先给题目、100—200 字预览、证据边界和去重判断，确认前不生成；要求“确认后发送”时先完成并交付可审阅文件，确认前不发送。不得把这些条件扩展为所有任务的重复确认。

## 核心写作规则

- 新写或实质改写先查可用既有稿及登记，按 `政策对象 + 核心问题 + 主要制度工具 + 管辖层级` 语义去重。报告检查范围和新增/延续边界；清单不可访问不声称完全无重复，不擅自删除或合并用户指定篇目。
- 法律、统计、政策状态、机构职责及案例优先核验当前有效的一手来源。记录发布者、定位、发布日期、统计/适用期、地域及支持范围；新发布日期不等于新统计期。
- 区分已核实事实、用户确认、来源观点、合理推断和政策建议。编号引用缺少原文只能作线索；用户确认不替代独立核验。无证据的数字、案件、调研经历和绝对判断删除或降级，待核项留在内部记录，不靠定性措辞掩盖关键证据缺口。
- 摘要先用普通读者能理解的语言解释主题核心概念，再提炼主要问题、原因或后果及三条对策的主线，使读者只读摘要即可把握全文。不得用一组新术语解释另一术语，或只写背景和建议而省略问题。
- 样稿控制文风和已授权的署名，不提供新主题的政策事实。采用“摘要—现状—问题—对策”的论证骨架；咨政报告保留这一文体结构，不因技能名称而改成提案。未指定篇幅时参考2400—3000汉字，把正文重心放在现状和问题：现状有可核实的数据及口径，问题有具体实例、机制和影响。逐项区分实际发生的问题、试点局限与风险推断；证据不足时补查、缩小结论或删去，不为凑数据或案例编造事实。
- 对策恰好三条，围绕主线归并、精炼；保留主责机关、关键动作及必要程序与边界，不把多组无关措施塞入三个长段落。问题数量由独立机制和证据决定，不要求与建议等数。总标题、小标题及领起句精炼、具体、用词自然变化，不强求对仗或等字数；准确术语保持一致。新增资源、数据处理或权利限制须交代权限、实施成本、监督救济及调整退出，拟定期限与指标明确作为建议。
- 问题分析是正文重点：从具体障碍出发，以真实案例和适用数据解释发生机制、现行制度的执行或衔接缺口，以及对具体人群和实际运行的影响。不能停留在现象罗列或“重视不够、机制不健全”等空泛归因；有依据的因果关系与仍需验证的推断分开表达。
- 优先选用与论点直接相关、近期受到关注、公众较熟悉且容易理解的真实案例，用简短背景说明发生了什么、影响谁、暴露哪个具体环节。热点只是选材优先项，热度不能证明真实性、代表性或因果；核对原始材料及后续调查、澄清和处置进展。没有合适热点时，采用可核实、贴近日常生活或生产的典型案例，不硬套热点或把假设当实事。
- 数据采用写作时最新已公开、可核实且与问题直接相关的统计期；检索发布机构是否已有更新或修订，分别记录发布日期和统计期。解释数字说明的规模、趋势或差异，保持对象、地域、单位、分母和比较口径一致。最新完整年度与近期月度、季度数据按用途区分；历史数据明确年份和用途，没有可靠新数据时说明可用资料的时限，不以转载日期、预测或估算冒充最新实绩。

## 按需执行

- 以白皮书、券商研报、咨询机构或其他研究报告为素材撰写政策稿，或要求删除正文中的研报转述：读取 [研究材料转为直接论述](references/research-to-policy.md)。默认正文直接写事实、机制和建议，不反复介绍报告或机构；证据归属留在内部，统计口径与不确定性保留。
- 新写、改写、批量选题或处理评论材料：读取 [写作框架与文风](references/writing-framework.md)。纯排版、拆分无需加载写作案例。
- 要求意思不变地缩短、合并问题建议、比较版本、严格评分再改稿：读取 [精简重组与五项自评](references/revision-compression-review.md)。锁定原意和比较基准，按机制重组后复核；加厚增加有效制度内容，精简删除冗余，两者不矛盾。需要具体示例时再读该参考链接的案例，不将个案数字移植到新题。
- 成稿语言复核：新写或实质改稿完成事实、权限和论证核验后，制作 Word 前，读取 [提案成稿语言复核](references/policy-language-review.md)，按内容保真、表达改善、过程留痕三项标准验收。纯排版、拆分不自动触发语言改写。
- 制作、拆分或检查 Word：读取 [Word 命名与版式](references/word-style-profile.md)，使用当前 `$documents` 技能。按其要求完成生成标记、结构检查和全部页面渲染；改动后检查最终版本。字体替代要披露，缺字或渲染失败不能声称视觉核验通过。
- 用户要求邮件交付：读取 [固定收件人邮件交付](references/email-delivery.md)，再调用 `$gmail-send-to-917935736`。默认收件人为 `917935736@qq.com`；只调用写作技能或修改技能不自动发送，也不代表永久发送授权。
- GitHub 仅在用户明确要求同步/发布时使用；核对准确仓库、分支、路径、可见性和提交内容，保留原内容并回读核验。提及 GitHub 不构成上传要求；不猜仓库或创建未知仓库。

## 交付与状态

交付前核对：摘要是否解释概念并概括全文，问题是否讲清事实、机制、制度缺口与影响，案例是否真实、相关且让非专业读者容易理解，热点是否核查后续进展，关键数据是否检查最新发布与修订并标明统计期，结论是否超出证据，对策是否恰好三条。交付最终文件路径、各篇实际字数/字符数及口径、署名情况、结构和 QA 状态。来源默认留在内部记录，对外正文不追加来源/核验段落，除非用户要求。关键事实或署名等报送要求未满足时说明具体缺口，不称可报送；文档通过核验不等于已提交或采用。邮件状态与文稿完成状态分别报告。
