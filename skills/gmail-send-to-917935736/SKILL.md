# 可靠邮件交付至 917935736@qq.com

目标是发送正确附件并取得可核查的 Gmail 已发送证据，不保证所有环境允许发送，也不把已发送等同于收件人已收件或已读。诊断请求只读，不授权重发。

## 必须执行

1. 锁定当前用户授权的收件人和具体文件版本。记录绝对路径、文件名、非零字节数、MIME、SHA-256；不猜“最新版本”。文件夹须先确认独立附件还是压缩包，不擅自打包、改内容或分享链接。
2. 检查当前会话可用工具及其发送/附件参数，读取 Gmail profile 获取发件邮箱。历史成功、截图中的 BLOCKED 或笼统的旧报错均不能代替当前能力证据。仅未发现工具时可继续查找允许的连接器；明确权限禁止时立即停止。
3. 多附件或原始附件经 base64 后可能较大时，读取 [分批与预检](references/batching.md)，运行 `scripts/preflight.mjs`。预算是请求大小，不是 Gmail 邮箱容量。脚本只规划，不发送，也不授予权限。
4. 已授权发送但需拆为多封时，先告知分组并取得确认；已在本轮明确允许分批无需重复询问。逐封执行，不并发发送。每次发送前展示发件人、收件人、主题、完整正文、全部附件名；重新核对文件哈希。文件改变则重做预检。
5. 首选允许的 Gmail 附件发送工具，UTF-8 正文和 `multipart/mixed` 附件，文件名、MIME、附件字节保持不变。仅在连接器没有发送能力且没有权限拒绝时，可使用当前会话允许、已登录的 Gmail UI；不得借 UI、脚本、SMTP、换账号规避拒绝。
6. 每封发送后独立搜索 `in:sent to:917935736@qq.com subject:"完整主题" has:attachment newer_than:1d`，必要时使用覆盖实际发送时间的绝对日期。读取结果，核对发送返回的 message ID、SENT 标签、From/To/Subject，以及每个附件的名称、字节数、MIME和总数量。不可把 draft ID 或 thread ID 当 message ID；UI缺少必需证据时标为 UNVERIFIED。
7. 记录每批 message ID、附件清单和状态，全部批次核验通过才能报告全部成功。某批失败则停止后续发送，保留已完成批次，不重发成功批次。发生错误时只读 [失败处理](references/failures.md)。

## 状态与验收

- `SENT_VERIFIED`：发送结果与独立已发送记录完全匹配。
- `DRAFT`：仅生成草稿，尚未调用发送。
- `BLOCKED`：有明确的未发送原因，如权限拒绝、失效登录、缺文件或单附件超限；说明已完成批次和所需用户动作。
- `UNVERIFIED`：已尝试发送但结果或复核不明确；先查已发送，不自动重试。

最终答复简述收件人、已核验邮件数/附件数、未完成项。证据记录保存在任务目录，不保存令牌或附件base64到报告。没有当前证据不得宣称成功。技能更新、预检或离线测试均不授权发送测试邮件。
